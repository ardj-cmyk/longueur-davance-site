Vérifier un repo avant de l'installer

Un repo, c'est le dossier d'un projet : tous ses fichiers, et l'historique de chaque modification. Un repo public, tout le monde peut le voir et le télécharger. Mais c'est le code de quelqu'un d'autre. Voici ce que je vérifie avant qu'il touche à mon ordinateur.

Pourquoi c'est sérieux

Même nom, autre propriétaireEn août 2026, un projet populaire, book-to-skill, a été recopié par un autre compte, sous le même nom. La copie ajoutait du code qui fouillait les portefeuilles de cryptomonnaies et envoyait des fichiers vers l'extérieur. L'auteur original a publié un avis de sécurité dans son repo. Le détail du cas : installer un skill sans risque.

1Les 6 vérifications, sur la page du repo

  • Le propriétaire. Le nom du projet se copie en une seconde, le compte qui le publie, non. Va sur le site officiel de l'outil et regarde vers quel compte il renvoie.
  • Les étoiles et la date de création. Mille étoiles pour un repo créé la semaine dernière, ce n'est pas un succès, c'est une anomalie.
  • La dernière activité. Un outil qui dépend d'un autre service et qui n'a pas bougé depuis des mois est sans doute déjà cassé.
  • La licence. D'après GitHub, sans licence, les droits d'auteur s'appliquent par défaut : personne n'a le droit de reproduire, distribuer ou modifier le code.
  • Le fichier SECURITY.md. C'est la politique de sécurité du projet : les versions suivies, et comment signaler une faille. Certains auteurs publient aussi un avis de sécurité dans leur repo pour signaler les copies piégées de leur projet, comme celui de book-to-skill.
  • Les issues. L'onglet où les utilisateurs signalent les problèmes. Cherche « ne marche pas », « malware », ou le nom de ton système.

2Ce que fait vraiment le code

Les fichiers à regarder : ceux qui s'exécutent à l'installation. Un seul de ces signaux, et je n'installe pas :

  • Une commande qui télécharge et exécute du code sans le montrer (du type curl, puis bash).
  • On te demande de coller une clé API dans la conversation.
  • La vérification des certificats de sécurité est désactivée.
  • Le code va lire tes clés SSH, ton trousseau, tes portefeuilles crypto ou les mots de passe de ton navigateur.
  • Des données partent vers un serveur dont la documentation ne parle pas.
  • Du code caché (illisible, encodé) qui s'exécute.

3Fais-le faire par Claude, sans rien installer

Tu n'as pas besoin de savoir lire le code. Claude peut le lire pour toi, sans rien exécuter :

Audite ce dépôt GitHub sans rien installer ni exécuter : [colle le lien].
Dis-moi :
- qui est le propriétaire, et si le site officiel renvoie vers lui
- la date de création, le nombre d'étoiles, la dernière modification
- la licence, et s'il existe un fichier SECURITY.md
- ce que font les scripts d'installation : envoi de données,
  accès à mes fichiers, commandes administrateur.
Termine par un verdict : vert, orange ou rouge, avec la raison.

Les 3 règles

  1. Installe depuis la source officielle, jamais depuis un lien reçu en commentaire ou en message.
  2. Teste dans un dossier sans rien de sensible, pas là où sont tes dossiers clients.
  3. Dans le doute, tu n'installes pas. Il existe presque toujours une alternative plus sûre.

La même méthode vaut pour un skill et pour un MCP : installer un skill, brancher un MCP.
